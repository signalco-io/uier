# Notion integration: implementation plan

Status: adapter and project settings implemented. Provider registration and hosted acceptance remain manual release gates. This document retains the original design and proposed phases; [the implemented contract](integrations.md), [setup](integration-setup.md) and [operations](integration-operations.md) describe the current code and limits.

Architecture revised on 2026-10-28: Notion is the first provider on a shared integration layer. Separate plans cover [GitHub](github-integration-plan.md), [Linear](linear-integration-plan.md) and [Slack notifications](slack-integration-plan.md), including their verified API/authentication facts and remaining launch gates. All four adapters now share the implemented foundation; availability depends on each provider's configuration and acceptance gates.

## 1. Goal and scope

A workspace admin connects a project to a Notion database. Every thread the connecting admin can see, except private ones, becomes one Notion page that the scheduled worker keeps converged with the uier thread: properties (status, kind, environment, assignee, dates, links), feedback text and anchor, discussion, screenshot. Notion is a mirror; uier stays the source of truth.

Ships, in phases: connect and disconnect through Notion OAuth; choosing a data source and mapping its properties, with a template page so most admins skip the form; page creation and property updates; replies, edits, deletions and privacy changes mirrored; screenshots uploaded; "Open in Notion" links in the app and the toolbar; a bounded backfill.

The first release also establishes the provider contract, shared change discovery and delivery lifecycle, and multiple external links per thread (section 2.1). A project can connect several different services independently. Only Notion is implemented in these phases; the other services do not appear as available integrations until their own adapters, settings, tests and privacy copy ship.

Non-goals: two-way sync (phase 5 is a design only); webhooks; sending private threads (never, no switch); creating databases or properties through the API (not in the verified facts); a /status entry; permanent deletion of anything in Notion (the API has none); a Notion SDK; any sync from a request path or a detached promise; trashing pages when a project is marked done or its comments are turned off (open question 10).

## 2. How it works

A reviewer leaves or changes non-private feedback on a non-public project. Its source signal is committed independently of any previously loaded binding snapshot, so concurrent connection setup cannot lose the change. The mutation's etag-protected write also bumps `syncVersion` and sets `syncPending` on the comment; hard deletes write a tombstone in the same partition batch. Every five minutes the `Review notifications` workflow runs the worker; after the email step comes the integrations step: shared discovery durably fans each pending change out to a ledger for every bound connection before clearing the flag. Shared delivery leases each due ledger, re-authorizes and exports the thread through `projectFeedbackExport` under that connection's admin membership; the provider adapter plans and reconciles its external writes. For Notion this is a `notion-sync` ledger with page and block ids, hashes and cursors; app and toolbar receive an allowlisted external link.

```
reviewer / app / MCP
   |  non-public project mutation (etag write; private-only/no-op changes excluded)
   v
DbComment { syncVersion++, syncPending, syncKey }
   |  hard delete -> $tombstone_<id> in the same batch
   v  every 5 min, GitHub Actions "Review notifications", second awaited step
discoverIntegrationSync: listSyncPending() -> ledger per bound connection
                        clear syncPending only after all ledger writes and a version check
   v
processIntegrationSync: lease -> reauthorize -> projectFeedbackExport (never private)
                       -> provider adapter -> persist attempt -> external calls -> ledger updated
   v
Notion: page per thread; later adapters: issues or messages
App + toolbar: externalLinks[] (Notion first)
```

### 2.1. Expansion to other services

Keep the reliable delivery and access rules shared. Keep destination behavior in adapters. Adding a service should not add another comment mutation hook, pending flag, feedback export format or toolbar field.

| Shared layer | Provider adapter |
| --- | --- |
| `syncVersion`, pending discovery, tombstones and fan-out | Which supported changes produce external writes |
| Current admin membership, thread visibility and private-thread exclusion | Provider authorization or installation, scopes, token exchange/refresh/revocation |
| `FeedbackContext` / `FeedbackExport`, authorized screenshot access | Formatting, destination selection, field mapping and attachment handling |
| Durable ledger identity, leases, attempt persistence, retry scheduling and backfill | External ids, reconciliation, idempotency checks and error classification |
| Worker deadlines, fair scheduling and safe logs | Rate-limit buckets, request pacing and provider-specific pause reasons |
| Safe connection views, settings placement and external-link projection | Provider settings form, labels and verified external URL rules |

**Registry and contract.** Add `apps/web/src/lib/integrations/{model,registry,discovery,delivery,worker,links}.ts` alongside `syncSignal.ts`. The registry is a server-owned allowlist, initially only `notion`, with a typed adapter per provider. `IntegrationProviderId` grows when a real adapter ships. Each adapter declares its configuration check, supported delivery mode and capabilities, connection/configuration validation, pure projection from `FeedbackContext`, reconcile/send operations, external-link projection and rate-limit keys. The shared delivery runner owns the lease, persists each planned attempt before the adapter sends it, and saves the result under the same lease. Adapters classify results as accepted, waiting, failed, ambiguous or suppressed; they cannot clear source pending flags or acknowledge another connection's ledger. Unknown or unconfigured providers make no external calls and remain visible as unavailable work requiring attention; discovery leaves the source pending when it cannot durably queue a target.

`integrations/notion/{client,oauth,connection,page,transport,view,config}.ts` retains Notion-specific behavior. Its `delivery.ts` supplies the Notion adapter to the shared runner rather than copying `processNotificationDelivery`. Share the existing retry helpers with email, but retain email's event and delivery model; email is not migrated into this registry.

**Connections and identity.** `DbProject.integrations` is a partial map from registered provider id to `{ connectionId, since }`. Phase 1 allows one destination per provider per project; different providers coexist. All settings writes merge or remove only their own map entry under the project etag, including reconnect and database switches. A later need for several repositories or channels of the same provider can introduce multiple bindings without changing thread mutation signals: ledgers already identify `(provider, connectionId, projectId, threadId)`. Provider connection and ledger documents use the common envelopes in section 4 with typed provider-specific fields; a Notion page/block map is never required of another adapter. These are new planned records, so no shipped Notion records need migration.

A connection is the project's destination binding. A credential grant may eventually be shared by several bindings, for example an installation used by multiple projects. Keep that option behind the connection service: current Notion tokens remain per project unless open question 1 changes. Shared grant revocation must stop every binding using it; disconnecting one binding must not revoke a grant still used by another. Do not require all providers to have a Notion workspace, bot id, rotating refresh pair or OAuth flow. OAuth state is namespaced and checked by provider as well as user, workspace and project; token encryption context includes the provider. Each provider keeps its own configuration and least-privilege consent requirements.

**One discovery pass, independent progress.** Every eligible non-public project mutation records its signal in the same write, even when the request loaded the project before a binding was attached. A signal with no current targets is acknowledged without an external call. `hasIntegrationBindings(project)` describes current destinations; it never gates the source write. This corrects the original connected-project gate, which could lose a mutation racing with setup. `discoverIntegrationSync` snapshots the current bindings, then idempotently upserts every target ledger with `requestedVersion = max(existing, observed syncVersion)`. Only after every upsert succeeds may it clear the source flag with the original version/etag guard. A crash after the first target leaves the flag pending; replay upserts the same ledgers without duplicates. Discovery persists work even for paused or turned-off connections; delivery waits independently for each to resume. A newly attached connection receives subsequent changes and an explicit backfill for existing threads; it does not inherit another provider's processed cursor. Discovery checks the current binding map again before acknowledging the source etag. This is a defensive recheck, not a cross-container transaction. Older committed source state remains pre-activation history unless explicitly backfilled; Slack applies its destination-generation cutoff independently.

All non-public project hard deletes write an atomic tombstone, even when the request saw no bindings. Tombstones capture the deletion version and known target identities without feedback text; discovery unions these with current bindings before acknowledgement. Discovery transfers `deletion: { version, deletedAt }` to all target ledgers before deleting the tombstone; each ledger retains that intent and its external ids until cleanup is processed. Delivery uses the intent without needing the deleted comment or tombstone. One provider must never delete the shared tombstone while another still needs it. The 30-day tombstone TTL bounds recovery if discovery is unavailable that long; it is not evidence that external copies were removed.

`runIntegrationWorker` discovers once, then gives each registered provider a bounded turn and its own persisted retry state. A rate limit, reconnect requirement or failure in one provider must not stop another provider from being attempted. Divide the remaining wall-clock budget fairly and rotate the starting provider between runs; each adapter accounts for its calls within that allowance. Notion's bot/workspace limit keys and eight-minute cap stay inside its allowance. Logs and retry controls identify the provider and ledger. Re-read the binding, enabled state, connecting admin and visibility before external delivery; a disconnected binding suppresses only its own ledgers and links. Private transitions and deletions use the adapter's cleanup path without exporting private content. If cleanup is unsupported or fails, hide the link and report the limitation; never claim the external copy was deleted.

**Different destinations, different behavior.** The following summarizes the provider plans. Their linked documents own provider-specific API facts and release gates; these services do not ship as part of the Notion phases:

| Provider | Candidate destination and delivery mode | Decisions needed in its own plan |
| --- | --- | --- |
| Notion | Data source; continuous page mirror as specified here | Existing mapping, reconciliation, trash and upload rules |
| [GitHub](github-integration-plan.md) | Repository; one-way issue mirror after the admin enables it | Installation/authentication, label/status/assignee mapping, discussion, attachments and cleanup limits |
| [Linear](linear-integration-plan.md) | Team/project; one-way issue mirror after the admin enables it | Authorization, destination selection, workflow mapping, discussion, attachments and cleanup limits |
| [Slack notifications](slack-integration-plan.md) | Channel; notifications grouped by uier thread | Authorization, distribution, channel access, selected changes, coalescing, duplicate prevention and cleanup limits |

A notification adapter may coalesce several changes into the current state. If its product contract promises every event, add a durable event stream in that provider's plan; the shared `syncVersion` cursor is a state signal and does not preserve intermediate events. Capabilities must explicitly describe edits, replies, attachments, status mapping, cleanup and inbound support. Unsupported capabilities are stated in settings and docs, not silently mapped to Notion behavior. Two-way sync and webhooks remain separate provider designs; the common layer does not authorize inbound writes.

**Adding a provider.** Verify its official API/authentication, rate limits and retention behavior; choose its delivery mode and destination rules; implement and register the typed adapter, connection flow and settings form; add contract tests and a provider stub; update configuration, operational docs and privacy copy for exactly the data it sends. Run the shared multi-provider acceptance cases in section 12. The second adapter should require no changes to comment mutations, pending discovery or the external-link DTO. Build only the Notion adapter and the small shared contract now; add new capabilities when a real provider needs them.

## 3. Notion facts the design depends on

- Connection type: uier is one public connection (Notion's current name for a public integration) registered once in Notion's developer portal; customer admins authorize it through OAuth, so no customer creates anything in the portal. Internal connections and personal access tokens are single-workspace or single-user static tokens and do not fit. A public connection's installation scope is `Any workspace` or `Selected workspaces only` and cannot change after creation. Notion's security review applies only before a Marketplace listing; a public connection works with OAuth without one. Plain `http` redirect URIs are accepted only for `localhost`, not `127.0.0.1`.
- OAuth: authorize URL with `client_id`, `redirect_uri`, `response_type=code`, `owner=user`, `state`; callback `?code&state` or `?error=access_denied`; `POST /v1/oauth/token` (HTTP Basic) returns `access_token`, nullable `refresh_token`, `bot_id`, `workspace_id`, `workspace_name?`, `duplicated_template_id|null` (the id of the duplicated template page). Refresh rotates both tokens; no `expires_in`; removal in Notion gives `invalid_grant`; a [token revocation endpoint](https://developers.notion.com/reference/revoke-token) is available (uier disconnect currently removes local authority and credentials without calling it); access is per authorizing user and every authorization mints a fresh pair.
- `Notion-Version: 2026-03-11` (`in_trash`, `position` instead of `after`). Schema lives on the data source (`GET /v1/data_sources/{id}`: `properties` keyed by name with `{id, name, type, options}`, `in_trash`, 404 when unshared); create with `parent {type:"data_source_id"}`; query with `POST /v1/data_sources/{id}/query`; search filtered to `data_source`. Trashed pages stay addressable with `in_trash: true`.
- Writable properties: `title`, `rich_text`, `select {name}` (auto-created, no commas), `status {name}` (the option must exist in the schema; a page write never creates one, although since March 2026 the Update data source endpoint can, which uier does not use), `date {start}`, `url`, `files [{type:"file_upload"}]`; array writes replace; `properties` keys may be property names or ids on both `POST /v1/pages` and `PATCH /v1/pages/{id}` (verified against both references), so payloads are keyed by id. `PATCH /v1/pages/{id}` also accepts `erase_content: true` (deletes every child block, irreversible through the API) and `notifications: { mode: "silent" }`.
- Blocks: `GET /v1/blocks/{id}/children` lists a block's or page's first-level children (paginated with `start_cursor`, `has_more`, `next_cursor`; a `child_database` block carries the database id); append children (100 per call, `position: { type: "after_block", after_block: { id } }`, or `start` / `end`, replacing the old `after`), `PATCH /v1/blocks/{id}` for same-type content, `DELETE /v1/blocks/{id}` trashes; `PATCH /v1/pages/{id}` updates properties and `in_trash`; `code` blocks need a `language`. Limits: 500 KB per request, 100 children per create, 100 per array, 2000 characters per rich text and URL.
- Uploads: `POST /v1/file_uploads` returns `{id, upload_url, expiry_time}`; `POST /v1/file_uploads/{id}/send` (multipart `file`); attach within one hour, permanent afterwards; cap from `GET /v1/users/me` (5 MiB free).
- Rate limits: 180 requests per minute per connection on Free/Plus, 600 on Business/Enterprise, plus a workspace budget shared by all connections whose `Retry-After` can exceed 60 s (`additional_data.rate_limit_reason`). 429 and 529 retry after `Retry-After`; `public_api_request_blocked` is never retried.

## 5. Connect and disconnect

Both routes live under `app/(rest)/(app)/app/notion/` (so `proxy.ts` sends visitors without a session cookie to sign-in) and are declared in `apps/web/src/knownPages.ts`. A cookie that no longer verifies (`getAppContext()` null) redirects to `/app/sign-in?next=/app`; code and state are never carried through the sign-in document, the admin starts again.

`GET /app/notion/connect?project=<id>` (`connect/route.ts`, `dynamic = 'force-dynamic'`): `getAppContext()`; not admin or `!isNotionConfigured()` redirects to settings with `?notion=unavailable`; `getProject(context.workspace.id, project)` or 404; `project.id === PUBLIC_PROJECT_ID` is 404. A `Sec-Fetch-Site` other than `same-origin` or `none` redirects to settings without minting (the session cookie is `sameSite: 'lax'`, so a cross-site link could otherwise start the flow). A `connected` connection with a data source redirects with `?notion=already`; `needs_reconnect`, `paused` or none continues, so "Reconnect" uses the same route. Mint `state = randomToken()` (nothing identifying leaves uier), write the `notion-oauth-state` document with `updateDoc` or `create` (one per provider, user, workspace and project), answer 302 with `Cache-Control: no-store` to the authorize URL with `redirect_uri = `${await appBaseUrl()}/app/notion/callback``. The settings card links here with a plain `<a>` in `Button asChild`, never `next/link` (prefetch would mint state documents). On previews `isNotionConfigured()` is false, so no preview redirect URI is ever registered.

`GET /app/notion/callback` (`callback/route.ts`): `getAppContext()`, then the pure `resolveOauthCallback({ user, state, code, error })` from `apps/web/src/lib/integrations/notion/oauth.ts`, then a redirect; the handler holds no logic. `resolveOauthCallback`: `isRandomToken(state)` or 400 "This connection link is not valid. Start again from the project settings."; for every outcome it first finds the state document with `provider: 'notion'` whose `stateHash` equals `sha256Hex(state)` under `user:<uid>` and deletes it (`store.delete` must return true: single use and user binding in one step); `getMember(wid, uid)` must be admin and the project must exist in `wid` (the workspace cookie is not trusted); `error=access_denied` then redirects with `?notion=denied` and writes nothing; any other `error`, or an exchange that fails (`invalid_grant` from an expired or reused code, `invalid_client`, 429, timeout) redirects with `?notion=failed` and writes no connection. Exchange the code (15 s timeout), then `store.create` the connection with `status: 'connected'`, `enabled: false`, `maxFileUploadBytes: 5 MiB` (the real cap is read on the first worker run, so the callback does not depend on `GET /v1/users/me`), or `updateDoc` an existing one: `connectedBy = user.id`, new tokens, `generation + 1`, `notionWorkspaceId`, `notionWorkspaceName` and `botId` from the response, status reset, codes cleared; when `workspace_id` differs from the stored one, also clear `databaseId`, `dataSourceId`, `dataSourceName`, `mapping`, `schema`, set `enabled: false` and remove `project.integrations.notion`. A missing `workspace_name` shows as "Notion workspace" with the bot id in mono.

Template: `duplicated_template_id` is a page id. Resolve it with `GET /v1/blocks/{id}/children` (paginated), take the first `child_database` block, then `GET /v1/databases/{childId}` to `data_sources[0]` (a `child_database` block id is the database id; a 404 there falls through to the manual picker); if `GET /v1/databases/{duplicated_template_id}` succeeds first (full-page database template) use it directly. Read the schema and apply the default mapping. When neither yields a data source, the connection is stored without one and the admin picks with "Load databases". Redirect to `${KnownPageLinks.projectSettings(id)}?notion=connected#notion`.

Token storage (`apps/web/src/lib/app/secrets.ts`): AES-256-GCM via `node:crypto`, 12-byte random IV, 16-byte tag, serialized `k1.<iv>.<ciphertext>.<tag>` base64url; AAD `notion-connection:<workspaceId>:<projectId>:<access|refresh>`; key `NOTION_TOKEN_KEY` (32 random bytes, base64), required unless `isLocalRuntime()`, where a fixed key derived from `'uier-local-development'` is used, mirroring `serverSecret()`. The key is separate from `UIER_COMMENTS_SECRET` so each rotates alone; `k1` is the key id for a future `NOTION_TOKEN_KEY_PREVIOUS`. Decrypted tokens exist only in worker and action memory, never in DTOs, views, action results, ledgers or logs.

Who may use the token: the worker, and the server actions Load databases, save mapping, Send existing comments, Turn on and Reconnect. Each first requires `getMember(connection.workspaceId, connection.connectedBy)?.role === 'admin'`; otherwise it wipes `tokens`, sets `needs_reconnect` / `member_left` and answers the "Member left" copy without decrypting. `revokeNotionGrantsOf(workspaceId, userId)` (`connection.ts`) does the same for every connection of the workspace whose `connectedBy` is the user; `revokeIntegrationGrantsOf(workspaceId, userId)` dispatches to the registered adapters, including this helper; `removeMember` in `apps/web/src/lib/app/invitations.ts` calls the shared helper (there is no role-change action today; one added later must call it too). The grant is personal to the authorizing user, so it ends with their admin role.

Refresh, race free (`connection.ts`): on 401 `unauthorized`, `refreshConnectionTokens(connection, generationUsed)`: (1) re-read; if `tokens.generation > generationUsed` return the current tokens; else `updateDoc` that throws `RefreshInProgress` when `refreshLease` is unexpired (ledger `waiting`, `nextAttemptAt = now + 60 s`; an action answers "Notion is busy. Try again in a minute.") and otherwise sets a 2-minute lease; (2) refresh grant; (3) one lease-checked `updateDoc` writes both ciphertexts, `generation + 1`, clears the lease; (4) `invalid_grant`: `needs_reconnect`, `invalid_grant`, tokens wiped; (5) other errors clear the lease and the caller backs off. Worker and actions share the lease. A crash between (2) and (3) loses the pair and ends in `needs_reconnect`; documented limitation.

Disconnect (`disconnectNotionAction`, `appContextOrThrow({ admin: true })` + `adminProject(formData.get('projectId'))`, exported from `apps/web/src/components/app/projects/actions.ts`): removes only `project.integrations.notion` through the provider-scoped project helper, deletes the Notion connection document, and sets only that connection's ledgers `active: false, status: 'suppressed'` but keeps them. Other bindings, credentials and ledgers are untouched. Nothing is called in Notion. Reconnecting to the same data source adopts existing pages through the uier id query. The product has no project or workspace deletion today; when one arrives it must disconnect all provider bindings, wipe their credentials (respecting any shared grants) and delete the project's ledgers.

## 6. Choosing the database and mapping properties

Data sources are listed only inside a server action ("Load databases"), never at settings render: `POST /v1/search` with `{ filter: { property: 'object', value: 'data_source' }, page_size: 100 }`, paginated to 500, `in_trash` filtered, shown in a shadcn `Select` by `name` (bounded, stripped of control and bidi characters, untrusted) with the parent database id in mono when names collide; the template's data source is preselected.

Schema: `GET /v1/data_sources/{id}`; keep per property `{ name, type, options }` under its id; 404 means not shared. The worker re-reads the schema when `schemaCheckedAt` is older than 24 hours or after a `validation_error`, and `GET /v1/users/me` for `maxFileUploadBytes` on the same cadence. Mapping is stored by property id and payloads are keyed by property id (accepted by create and update page), so a rename in Notion changes nothing; the cached schema is still re-read for types and option names. Defaults are applied by exact name and type match on first read; unmatched rows start as "Not sent". `title` (read only) and `uierId` (a `rich_text`, default "uier id") are required; the template carries both. Saving a different `dataSourceId` keeps the ledgers; pages are recreated in the new database on the thread's next change (section 7).

| uier field | Notion type | Default property | Value |
| --- | --- | --- | --- |
| title | title | (the title) | `context.title` (100 chars, "Suggested rewrite: " prefix kept) |
| uier id | rich_text | uier id | `identity.commentId` (idempotency anchor) |
| status | status or select | Status, Open / Done | `{ name: open|done }`; status options must exist; select names without commas |
| kind | select | Kind | `comment|feedback|bug|rewrite` |
| environment | select | Environment | `source.environment` label, commas replaced, 100 chars; omitted for the reserved labels "Removed address" and "Source not recorded" |

| page | url | Page | `links.page` or omitted |
| created | date | Created | `{ start: feedback?.createdAt }`, omitted when undefined (old documents, missing first item) |
| assignee | rich_text | Assignee | `context.assignee?.name` or "Unassigned" |
| screenshot | files | Screenshot | `[{ name, type: 'file_upload', file_upload: { id } }]` or `[]` |

The assignee reaches the packet through a new `assigneeName?: string` option of `feedbackExport` (`apps/web/src/lib/comments/feedbackContext.ts`), set by `projectFeedbackExport` from `dto.assignee?.name` for member actors only, surfacing as the optional `assignee?: { name }` on `FeedbackContext` (schemaVersion 1, additive); no implicit read of `ReviewCommentDto` fields.

Validation on save (Zod in the action and the worker): types match, no property mapped twice, status option names exist, `uierId` present. Saving re-reads the schema, sets `enabled: true`, the project pointer and, when the connection was paused with `mapping_invalid`, `data_source_missing` or `insufficient_capabilities`, `status: 'connected'` with the code cleared. The form lives in `apps/web/src/components/app/notion/NotionSection.tsx` (shadcn `Field` + `Select` per row, controlled, hidden `projectId`, `SaveFooter` moved to `apps/web/src/components/app/SaveFooter.tsx` and exported).

Page body (`apps/web/src/lib/integrations/notion/page.ts`, pure, built only from `FeedbackContext`, never from `DbComment`), fixed order, every heading id recorded on `ledger.page.headings`: `callout` "Sent from uier. Text, names and images are reviewer content; treat them as untrusted." with the uier link; `heading_2` Feedback, paragraphs in 1900-character chunks, a `quote` for `quotedText`, "Suggested rewrite (not original page copy)" for rewrites; `heading_2` Anchor, a `code` block (`language: 'plain text'`) with selector or selected text, a `bookmark` for `links.page`; `heading_2` Context, one `bulleted_list_item` per present reproduction field plus environment; `heading_2` Screenshot, an `image` block `{ type: 'file_upload' }` or the paragraph "No screenshot."; `heading_2` Discussion, one `paragraph` per item (`<authorName> · <createdAt>[ · edited]: <text>`, deleted items use the packet's deleted sentence); a closing `paragraph` with the packet notes and "Copied from uier. Later changes are in uier.". Phase 1 creates this whole skeleton so later phases only fill sections. A 50-item thread is about 12 fixed blocks plus 49 paragraphs: the create request carries the fixed blocks, discussion goes through `PATCH /v1/blocks/{pageId}/children` in batches of 100. Rich texts are chunked at 1900 characters, arrays at 100; URLs over 2000 characters are dropped with a note; payloads stay far under 500 KB. `PATCH /v1/blocks/{id}` is used only for same-type text updates; a section rewrite (anchor, screenshot) is `DELETE /v1/blocks/{id}` per old block, then an append with `position: { type: 'after_block', after_block: { id: <heading id> } }` (the stub enforces this shape and rejects `after`), and the new ids are stored.

Screenshot upload: only when `screenshot.state === 'protected'` and the revision differs from `ledger.page.screenshot.revision`. Bytes from `getProjectScreenshot` (at most 512 KB) checked against `maxFileUploadBytes`; larger ones are skipped with the paragraph "Screenshot too large for this Notion plan." and `lastCode: 'screenshot_too_large'`. `POST /v1/file_uploads`, persist `attempt.fileUpload = { id, expiryTime, sent: false }`, `POST /v1/file_uploads/{id}/send` (hand-built `FormData` with a `Blob`), persist `sent: true`, attach in the same run; `ledger.page.screenshot.fileUploadId` is written only after the attach succeeded (the moment it becomes permanent). On a retry, `sent` false or `now >= expiryTime - 60 s` starts a new upload, never a resend; a `validation_error` on an attach past `expiryTime` is `pending` with a new upload, not `mapping_invalid`. An attached id is reused on rebuilds. External file URLs are never used because uier's screenshot URLs are access checked.

## 7. Sync semantics

The worker projects state; it does not replay event kinds. `withSyncMark(project, before, after)` (`apps/web/src/lib/integrations/syncSignal.ts`) returns `{ ...after, syncVersion: (after.syncVersion ?? 0) + 1, syncPending: true }` when the exact non-public project partition matches, `after !== before` (the status no-op returns the same object and is not marked) and the thread is not private both before and after (`private || isPrivateAppFeedback`; a thread private from creation creates no ledger, the toggle in either direction does); else `after` unchanged. It is applied once per mutation, at the service layer that holds the project: `createProjectComment` (before the write), `replyToProjectComment` (both the `commitReplySubmission` prepare callback and the `updateComment` path; the MCP tools `reply_to_feedback`, `set_feedback_status` and `assign_feedback` reach these same functions), `changeComment.apply` (status, private, assignee, both edits), the two non-null branches of `deleteProjectCommentItem`, and a new optional `finalize(comment)` argument of `reattachAnchor` and `replaceSavedScreenshot`. Not in `withNotificationEvent` or `updateComment` (verified: `changeComment.apply` runs inside `updateComment`, so marking both would double count). `notificationEvents` and `notificationPending` are untouched.

Tombstones: `updateComment` gains an optional fourth argument `onDelete?: (comment: DbComment, etag: string) => Promise<ConditionalWriteResult>`; when `update` returns null it calls `onDelete ?? ((_, etag) => store.delete(partition, id, etag))`, keeping the `not_found` and `conflict` mapping and the retry loop. `removeProjectComment` and `deleteProjectCommentItem` pass `(comment, etag) => project.id !== PUBLIC_PROJECT_ID ? store.deleteWithTombstone(partition, id, etag, syncTombstone(project, comment)) : store.delete(partition, id, etag)`; `hadScreenshot` and `forgetScreenshot` stay as they are.

| uier change | Notion operation |
| --- | --- |
| thread created, backfill | `POST /v1/pages` (properties + fixed skeleton), then discussion batches |
| reply | append missing discussion paragraphs |
| any item edit | `PATCH /v1/blocks/{blockId}` when `textHash` differs; first item also updates the title |
| reply deleted / first item placeholder | `PATCH` the block to the deleted sentence; image block trashed; properties cleared |
| resolve/reopen, assignee, environment, anchor | `PATCH /v1/pages/{id}` with changed properties only; anchor section rewritten |
| screenshot new or replaced | upload; files property replaced; screenshot section rewritten |
| made private | page emptied, then trashed: one `PATCH /v1/pages/{id}` with `erase_content: true`, the title "Removed from uier" and every mapped property cleared (status untouched), one append of the paragraph "This comment was made private in uier.", then `{ in_trash: true }`; ledger `suppressed`, page id kept |
| visible again | `{ in_trash: false }`, then a full rebuild |
| hard delete (tombstone) | the same emptying and `{ in_trash: true }` when the ledger has a `page`, otherwise no call; this connection's ledger becomes `accepted`, `tombstoned: true`, `processedVersion = requestedVersion` after cleanup; shared discovery alone deletes the tombstone after fan-out |
| `ledger.page.dataSourceId !== connection.dataSourceId` | page treated as absent: uier id query in the current data source, create when none, old page untouched, code `page_moved_database` |

Notion's trash is readable and restorable by its workspace members, and Notion keeps page history and attached files; `erase_content` is irreversible through the API but says nothing about page history, so emptying before trashing limits what stays there and nothing uier does removes it (section 11 says so). Updates to existing pages are sent with `notifications: { mode: 'silent' }` so a mirrored edit does not notify the Notion workspace; creates keep Notion's default.

Ordering: one thread at a time under the ledger lease; across threads sequential by `nextAttemptAt`; discussion paragraphs appended in `createdAt` order, never reordered. Cursors: `requestedVersion` merged with `max` on discovery; a run sets `through = comment.syncVersion` at projection time; a mutation during the run raises `requestedVersion` and keeps the ledger active. Shared discovery clears `syncPending` only after every target ledger is durably upserted and `syncVersion` still equals what it saw, by etag replace, ignoring conflicts. No provider delivery path clears this shared flag.

Idempotency: one ledger per (provider, connection, project, thread); `attempt.operationId` persisted before the first call; the `uier id` property equals the comment id. Before every `create` the worker queries `PATCH /v1/data_sources/{id}/query` with `{ filter: { property: <uier id name>, rich_text: { equals: commentId } }, page_size: 3 }`, ignoring hits with `in_trash: true`: one live hit is adopted (children listed once to rebuild the block map), zero creates a new page (a trashed hit was a deliberate Notion-side action and stays there), two or more stops as `ambiguous` with code `duplicate_pages`. A timed-out `create`, `update` or `append` is `pending`: the attempt is kept, `status: 'waiting'`, `nextAttemptAt = now + 60 s`, and the next attempt reconciles first (uier id query for `create`, children listing for `append` and `update`); `ambiguous` is reserved for `duplicate_pages` and for a reconciliation that still fails after `MAX_FAILURES`. Children are listed and diffed only on such a retry or when the block map is missing. No retry state lives in process memory.

Private threads: never sent. `comment.private || isPrivateAppFeedback(comment)` is checked before export on every attempt, independent of the admin's rights, in addition to `canSeeComment` under `memberActor(project, connection.connectedBy)` (no `agent`: the worker writes nothing in uier). The public project is never marked and cannot be connected (explicit 404 in the connect route and the actions).

Turned off (`enabled: false`): the connection and the project pointer stay; mutations keep marking and discovery keeps creating ledgers; the shared delivery runner skips ledgers of such a connection (`status: 'waiting'`, no calls, no failures). Turning on resumes and every waiting ledger converges with a full diff.

Backfill: "Send existing comments" lists `listProjectComments(project, actor)` (newest 1000, the `MAX_PROJECT_COMMENTS` cap, stated in the copy), skips private threads and stores the thread ids on `connection.backfill`; each run uses a shared enqueue helper to schedule the next 100 only for that connection, newest first. It queues a full projection at the current `syncVersion ?? 0` even when that version was already processed, merging with any newer pending version; it does not change the shared source flag or trigger another provider's notifications. The connection cursor advances only after the ledger writes succeed. The card computes "Sending N of M" from the `accepted` ledgers among those ids for that connection (two equality queries on `pk: notion:<projectId>`, on render, not cached); every create needs a query plus a create, so 100 queued threads take at least two runs under the budget.

Never done: permanent deletion; relying on Notion's trash as deletion; database or property changes; status option creation; writing to pages the ledger did not create or adopt in the current data source; reading Notion edits; calling Notion while paused, `needs_reconnect` or turned off; proactive refresh.

## 8. Delivery worker

`apps/web/src/lib/integrations/delivery.ts` owns the lifecycle for every adapter; `notion/delivery.ts` supplies Notion planning, reconciliation and result classification. For a Notion ledger: re-read; skip when `!active`, not due or leased; lease `{ id: randomUUID(), until: now + 5 min }` by etag replace; later saves through `updateDoc` with a lease-id check; attempt persisted before the external call; results mapped like email: `sent` clears the attempt (`accepted`); `pending` (429, 529, timeouts) keeps it, `status: 'waiting'`, `nextAttemptAt = now + Retry-After` (60 s when the header is missing or unparsable, capped at 24 h) and writes `pausedUntil` to every connection sharing the `botId` so sibling ledgers are skipped without calls; `failed` increments `failures` with `backoffMs = min(1 h, 60 s * 2^failures)` and stops at `MAX_FAILURES = 8`; `ambiguous` (`duplicate_pages`) sets `active: false`, keeps the attempt, stops for review; thrown errors store `error.name.slice(0, 80)`. `lastCode` carries `additional_data.rate_limit_reason` when present.

Client (`client.ts`): `AbortSignal.timeout(20_000)` per call; `NotionApiError` carries only `{ status, code, retryAfter?, requestId }` and a fixed message, never a request or response body or header, so `actionResult`'s fallback log cannot leak Notion content; server actions catch it and rethrow `UserFacingError` with the card's copy. Every id used in a path or filter must match `/^[0-9a-f]{32}$|^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/` and is encoded with `encodeURIComponent`; property ids are bounded to 64 characters of `[A-Za-z0-9%:_-]`; anything else is `invalid_notion_id` and pauses the connection as `mapping_invalid`.

Budgets are keyed by Notion connection, not uier project: the Notion adapter groups connections by `botId`, spaces calls 400 ms apart and allows 150 calls per `botId` per run; an in-run map keyed by `notionWorkspaceId` makes a workspace-level 429 skip the other connections of that Notion workspace for the rest of the run and pause them too. The worker starts no new ledger after `NOTION_RUN_BUDGET_MS = 8 * 60 * 1000` (the job has 20 minutes shared with email); the effective deadline is the earlier of this cap and the shared provider allowance. A budget exhausted mid-thread persists a `pending` attempt so a partial page can be reconciled on the next run.

| Notion answer | Ledger | Connection |
| --- | --- | --- |
| 429 `rate_limited`, 529 `service_overload` | `waiting`, no failure count | `pausedUntil` = `Retry-After` (default 60 s), on every connection of the bot |
| `public_api_request_blocked` | `waiting` | `paused`, `request_blocked`, never retried |
| 401 `unauthorized` | one refresh, one repeat | `needs_reconnect` on `invalid_grant` |
| 403 (`restricted_resource`, or any 403 on pages or blocks: a missing Insert or Update content capability) | `waiting` | `paused`, `insufficient_capabilities` |
| 404 data source, `in_trash` | `waiting` | `paused`, `data_source_missing` |
| 404 on a page the ledger owns | `page` cleared, code `page_removed_in_notion`, recreated on the next change after the uier id query | none |
| 400 `validation_error` on a page or block the ledger owns | first `GET /v1/pages/{page.id}` (counted): `in_trash: true` or not found is handled like the row above with code `page_trashed_in_notion`; a live page re-reads the schema, then `waiting` without failure count when a mapped property or option is gone, else `failed` | `paused`, `mapping_invalid` only when the page is live |
| 409, 5xx, network | `failed` with backoff | none |
| connecting admin gone or demoted | `suppressed` | `needs_reconnect`, `member_left`, tokens wiped |
| `enabled: false` | `waiting`, no calls | none |

Resume: saving the mapping clears `mapping_invalid`, `data_source_missing` and `insufficient_capabilities` (section 6); the worker also re-probes such a paused connection once per run with one `GET /v1/data_sources/{id}` when `schemaCheckedAt` is older than one hour and clears the pause when the probe and the mapping validation pass; `request_blocked` and `needs_reconnect` resume only through Reconnect. Scheduling: `apps/web/scripts/notifications-worker.ts` runs `runNotificationWorker` then `runIntegrationWorker(baseUrl)` (same production gate, `configuredAppBaseUrl()`), logs a separate `[<provider>] Checked N sync ledgers; M require review; K deferred for time.` summary for each provider and keeps exit code 1 for `failed`/`ambiguous` ledgers only, never for `needs_reconnect`. `@uier/toolbar/feedback-context` resolves to `dist/feedbackContext.js`, which the workflow builds before the run, and the client is plain `fetch`, so `run-notifications.mjs` needs no new `external`. `.github/workflows/notifications.yml` gains the input `retry_notion_sync` mapped to `UIER_NOTION_RETRY_SYNC`; `retryIntegrationSync({ provider, id })` validates the registered provider and its ledger id (`/^notion_[a-f0-9]{64}$/` for Notion), then re-queues only that provider's `failed`/`ambiguous` ledger keeping the attempt; `retry_notion_sync` passes `provider: 'notion'`. Documented escape hatch, not built: a sibling `notion-sync.yml` with its own concurrency group if Notion ever delays email digests, added to the `web` paths filter in `ci.yml`. Logs, in the worker and in actions, carry only the ledger id and a bounded code.

## 11. Security and privacy

| Threat | Defence |
| --- | --- |
| forged, replayed or cross-site OAuth start or callback | random state stored only as a hash under the user's partition, one per (provider, user, workspace, project), provider checked and state deleted on every callback; `Sec-Fetch-Site` check on connect; admin membership re-read from the store |
| stolen database or backup exposing tokens | AES-256-GCM with a key held only in Vercel, AAD bound to workspace, project and field |
| tokens or ids reaching a browser | `NotionConnectionView` allowlist; the RSC payload is asserted free of `tokens`, `k1.`, `refresh`, `botId`, `connectedBy` |
| two processes refreshing the same token | refresh lease, generation check before the call, atomic pair write |
| demoted or removed admin's grant kept alive | tokens wiped by `revokeIntegrationGrantsOf` dispatching to the adapter, and by every token-using action; `memberActor(project, connectedBy)` rebuilt per attempt |
| private or deleted content reaching Notion | actor-independent private check per attempt; privacy change and tombstone empty then trash the page |
| feedback text or tokens in logs, ledgers, action results | `NotionApiError` without bodies; bounded codes and hashes only; console spy and leak regex in tests |
| Notion content (names, titles, ids) treated as instructions or paths | stored bounded and stripped, rendered as text, never interpreted; ids validated by regex and encoded |
| retry storms on blocked or broken connections | `request_blocked` never retried; paused connections skip without calls; ledgers wait without failure counts |
| write amplification | source markers share the mutation write; bounded rotating discovery acknowledges unbound work without calls; tombstones expire in 30 days |
| browser contact with Notion | none: CSP unchanged; connect is a server 302, the callback a same-origin route |

Logging rules: `[notion] <ledgerId>: <code>` and the run summary only; never names, titles, text, URLs, tokens or Notion error messages.

```
A workspace admin can connect a project to a Notion database. From then on uier sends that project's comments to that database: the comment text and quoted text, the names shown in uier, the page address and the place on the page, the device details saved with the comment, the status and the assignee. Private comments are not sent. If a comment is made private or deleted after it was sent, uier empties its Notion page and moves it to the trash; Notion keeps trashed pages, page history and uploaded images under its own terms, and uier cannot remove them. To do this uier keeps the access token Notion issues, encrypted, until the admin disconnects, is no longer an admin, or Notion revokes it. We also store the name and id of the connected Notion workspace, which admin connected it, and, per comment sent, the id and address of its Notion page and hashes of what was sent, so later changes update the same page. Notion Labs, Inc. is a US company; the admin who connects it is responsible for that transfer under their own agreement with Notion, and we cannot delete or correct copies held there.
```

## 15. Risks and open questions

Risks: partial multi-provider fan-out losing work if the pending flag is cleared early (all-target durable upserts, version guard and crash/replay tests); provider coupling or starvation (independent ledgers, fair bounded turns and no provider-owned source acknowledgement); expiring an undiscovered deletion tombstone after 30 days (bounded recovery, never a deletion guarantee); treating notification delivery as a full mirror (explicit capabilities and provider-specific retention copy); refresh pair lost between the token call and the write (ends in a visible `needs_reconnect`, never silent); duplicate pages after a timed-out create (reconciliation before every create, `duplicate_pages` stops); rate limits spanning runs (persisted `pausedUntil` per bot, pacing, per-run and wall-clock budgets, "sending" not "sent" copy); the shared 20-minute job (8-minute Notion budget; the sibling workflow is the documented split); schema drift (re-read, specific pause codes, ids with name resolution); a second authorization of the same Notion workspace invalidating the first pair (production exit test, contingency named); `vercel pull` and sensitive variables (already proven by `UIER_COMMENTS_SECRET`; PR 1a logs presence); the `child_database` block id doubling as the database id (the template branch falls back to the manual picker when `GET /v1/databases/{childId}` answers 404); a connection created with the wrong installation scope (fixed at creation; the portal checklist and the phase 1 exit check it before any customer authorizes); cron delays (copy says "within a few minutes", docs say batching window); legal drift (pages edited in every phase that changes what is sent).

Open questions for the product owner, each with the assumed default:

1. Per-project connection (default) or one authorization per workspace with per-project databases.
2. Private threads never sent, no switch (default); an opt-in would first need a privacy policy change.
3. A page deleted or trashed in Notion: recreate on the next change (default) or leave the thread unsynced.
4. Trash the emptied Notion page when a thread is deleted in uier (default) or only empty it.
5. Backfill capped at the newest 1000 threads (default) or add a continuation to `listAll` now.
6. Operator-only retry through the workflow input (default) or a Retry button in the card.
7. The connection stays off the Notion Marketplace (default) or is listed there, which needs Notion's security review; the `Any workspace` scope keeps that option open.
8. Which Notion plan the first customers use (default Free/Plus, 180 requests per minute; budget constants stay editable).
9. Who owns the Notion developer portal account and the repository secrets (default: the repository owner).
10. Marking a project done or turning comments off leaves its Notion pages as they are (default), or trashes them through a project-level sweep that re-activates every ledger from the status and access actions.
11. After switching databases, threads are recreated on their next change (default) or immediately by a backfill.

## 16. Decision log

- Notion first, shared integration layer from phase 1: adapters for provider behavior, one fan-out discovery pass, connection-scoped ledgers and multiple external links. GitHub, Linear and Slack are future adapters with separately chosen delivery modes; they do not inherit Notion page or token assumptions.
- Winner: the converging ledgered mirror (design 2), chosen by two of three judges for idempotency and silent-mutation coverage; design 1's phasing and copy and design 3's write-path gate were grafted.
- Durable source markers on every eligible non-public project mutation at the service layer, independent of a cached binding snapshot, not in `withNotificationEvent` or `updateComment` (`changeComment.apply` runs inside `updateComment`); no mark for a status no-op or a thread private before and after.
- `syncVersion` as the single cursor instead of `activity.sequence` (silent changes) or a second `updatedAt` cursor.
- Required `uier id` property queried (trashed rows ignored) before every create; a timed-out call reconciles on retry instead of stopping as ambiguous.
- Mapping and payloads keyed by property id; both page endpoints accept ids as keys (verified on 2026-10-26), so renames in Notion never break the mapping.
- Emptying a page uses `erase_content: true` on the page update instead of deleting blocks one by one; updates to existing pages are sent silently.
- Status options are never created even though Update data source can since March 2026: uier does not change a customer's schema; the card asks the admin to add the option.
- Private threads never sent, checked independently of the actor; a page made private after sending is emptied then trashed, since Notion's trash is not deletion; `includePrivate` rejected because the privacy policy promises otherwise.
- Project done or comments off leave Notion pages alone (open question 10): `updateProject` emits nothing, and trashing a finished project's pages is a product decision.
- One uier public connection with installation scope `Any workspace`, unlisted: customers authorize it through OAuth and create nothing in the portal; internal connections and personal access tokens rejected (static, single-workspace or single-user tokens the customer would have to create and paste).
- Template page (`duplicated_template_id`, a page id resolved through its `child_database` block) instead of `POST /v1/databases` (not verified).
- Second awaited integrations step in the existing worker: one shared discovery pass, independent provider ledgers, fair provider turns and per-provider wall-clock/rate budgets; the separate workflow kept as an escape hatch.
- Ledgers kept after disconnect, with `dataSourceId` recorded so a database switch recreates instead of patching the old page.
- `pausedUntil` persisted per bot from `Retry-After` (60 s default) plus an in-run workspace map, instead of an in-process skip per project.
- Data sources loaded in a server action; the client component receives an allowlisted view, never the connection document.
- Random OAuth state stored as a hash, one per provider, user, workspace and project, consumed on every callback; a signed payload rejected because it would carry ids to Notion's logs.
- Grants end with the admin's role: tokens wiped on removal, demotion, `invalid_grant` and before any action uses them.
- Shared `notifications/retry.ts` instead of duplicating `failureCode`, `MAX_FAILURES` and backoff.
- A page removed or trashed in Notion is a normal event, never a connection pause; `needs_reconnect` never sets the exit code.
- Children list-and-diff only on a retry of a persisted attempt or a missing block map; visible `uier:<itemId>` markers rejected.
- Webhooks deferred to a design-only phase with raw-body HMAC, event-id dedupe and a Pulumi-held verification token; logging the token rejected.
- No SDK: the client pins the version, reads `NOTION_API_BASE_URL` explicitly, surfaces `Retry-After`, validates ids and throws errors without bodies.
- Notion is a recipient the admin chooses, not uier's processor; legal and card copy are phased so they never claim more than the shipped phase sends.
- No /status entry: `ServiceState` has no "not configured" value and the e2e server has no network.
- Cookie policy unchanged: the OAuth state is a URL parameter plus a server document.
